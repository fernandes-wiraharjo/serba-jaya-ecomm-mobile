# Instruksi agen untuk Serba Jaya Mobile

- Baca [status proyek](docs/PROJECT_STATUS.md), [arsitektur](docs/architecture/ARCHITECTURE.md), dan [pemetaan kebutuhan](docs/requirements/TRACEABILITY.md) sebelum mengubah kode. Gunakan [indeks](docs/DOCUMENTATION_INDEX.md) untuk dokumen terkait. Jika tersedia melalui kanal berizin, gunakan master prompt Phase 1 dan PDF asli sebagai referensi lokal. Indeks menjelaskan rujukan yang tersedia di repositori.
- Pertahankan Android dan iOS, modul feature-first Clean Architecture, MVVM pragmatis, Riverpod, GoRouter, dan Dio. Periksa implementasi sebelum menambah kode dan gunakan kembali komponen yang sesuai. Ikuti [standar penulisan](docs/development/CODING_STANDARDS.md). Buat fungsi dan file yang kohesif.
- Pertahankan flavor Android `dev`, `staging`, `prod` dan scheme iOS yang bernama sama. Pasangkan masing-masing dengan file `config/*.example.json` melalui `--dart-define-from-file` dan pertahankan validasi `APP_ENV` terhadap native flavor serta nama aplikasi. ID aplikasi yang disetujui ada di [panduan environment](docs/development/ENVIRONMENT.md). Perbarui tes dan dokumentasi ketika pemetaan berubah.
- Buat perubahan kecil dan mudah ditinjau. Hindari abstraksi prematur dan refactor di luar lingkup. Minta persetujuan sebelum tindakan destruktif atau perubahan arsitektur besar.
- Gunakan nama kode dalam bahasa Inggris dan dokumentasi dalam Bahasa Indonesia. Simpan teks pengguna di ARB. Jangan mengarang aturan bisnis, kontrak API, nilai desain final, atau kredensial. Catat ketidakpastian di [pertanyaan terbuka](docs/requirements/OPEN_QUESTIONS.md).
- Lindungi dokumen pribadi, token, dan materi penandatanganan. Jangan simpan atau tampilkan rahasia di kode, log, tes, atau dokumentasi.
- Implementasi reusable Bottom Navigation Bar dan Header mengikuti nilai Figma yang tercatat. Keterbatasan aset crop, pemetaan Header sementara, dan status perbandingan visual dijelaskan di [dokumen komponen](docs/components/BOTTOM_NAVIGATION_BAR.md) dan [Header](docs/components/HEADER.md). Jangan mengklaim pixel-perfect atau mengarang visual yang belum diverifikasi.
- Gunakan [sistem gerak terpusat](docs/architecture/MOTION.md) untuk rute, tab, dialog, dan bottom sheet. Hormati pengurangan gerakan dan navigasi kembali bawaan platform. Simpan stack tab dan gunakan Hero hanya untuk pasangan elemen yang sudah ada dengan tag unik per rute.
- Google Sign-In direncanakan menggunakan GCP OAuth 2.0 / OpenID Connect. Pertahankan dukungan Sign in with Apple. Pisahkan token identitas provider dari sesi backend. Tunda integrasi provider sampai disetujui. Firebase Authentication memerlukan persetujuan eksplisit.
- Jangan membuat OAuth client GCP, sertifikat Apple, atau signing key release sebelum disetujui. Jangan menebak fingerprint. Catat signing debug dan release secara terpisah di [data registrasi](docs/integrations/GCP_OAUTH_REGISTRATION.md). Lindungi keystore dan password. Jangan commit credential atau log rahasia.
- Tambah atau sesuaikan tes untuk perubahan perilaku. Jalankan format, analisis, serta tes yang relevan. Perbarui dokumentasi yang terdampak dan status proyek setelah perubahan signifikan. Laporkan hasil verifikasi aktual beserta blokir.

## Pengujian perangkat dan penggunaan sumber daya

- **Uji runtime hanya pada perangkat fisik Android/iOS.** Jangan menjalankan Android Emulator atau iOS Simulator, membuat virtual device, memulai Android Studio/Xcode secara otomatis untuk pengujian, atau mengunduh image emulator/runtime simulator.
- Sebelum menjalankan aplikasi, panggil `flutter devices` dan identifikasi perangkat mobile fisik yang benar-benar tersambung lewat USB atau wireless debugging. Jangan pilih simulator/emulator yang juga tercantum.
- Jalankan dengan ID fisik yang eksplisit, misalnya `flutter run -d DEVICE_ID --flavor dev --dart-define-from-file=config/dev.example.json`. Pertahankan flavor, file environment, application ID, bundle ID, sertifikat, dan signing yang sudah ada.
- Jika beberapa perangkat fisik tersambung, tanyakan kepada pengguna perangkat mana yang digunakan. Jika tidak ada perangkat fisik, lanjutkan implementasi source, `dart format`, `flutter analyze`, serta unit/widget test yang relevan; lewati runtime, laporkan pengujian fisik masih pending, dan minta pengguna menyambungkan perangkat saat runtime validation diperlukan. Jangan memakai emulator/simulator sebagai fallback.
- Bandingkan tampilan UI dengan Figma hanya menggunakan screenshot dari perangkat fisik tersambung. Jangan mengambil screenshot simulator sebagai bukti visual.
- Periksa ruang penyimpanan yang tersedia sebelum build. Pakai cache yang sudah ada, hindari `flutter clean`, build berulang tanpa perubahan source, build Android dan iOS secara paralel, atau proses latar yang tidak diperlukan. Utamakan hot reload/restart saat mengembangkan UI jika cocok.
- Jangan menghapus SDK, runtime, signing key, sertifikat, atau file lain yang tidak terkait. Perubahan sementara untuk uji build hanya boleh dilakukan jika file asli dapat dipulihkan secara persis dan hasil akhirnya dilaporkan.

## Integrasi Figma MCP

- Gunakan [panduan Figma proyek](docs/integrations/FIGMA.md) dan **Figma Console MCP (`figma-console`) sebagai server utama** untuk inspeksi desain Serba Jaya Ecommerce App (`gMs1cpj2AGfubJP8slp0yM`). Lakukan inspeksi hanya jika task secara eksplisit mengizinkannya. Utamakan Desktop Bridge dan operasi Plugin API lokal. Gunakan MCP resmi bernama `figma` hanya sebagai alternatif setelah pengguna menyetujuinya secara eksplisit.
- Sebelum membaca desain pada tiap sesi, periksa koneksi aktif dan lakukan probe Desktop Bridge, misalnya melalui `figma_get_status` dengan `probe: true`, `figma_diagnose`, dan `figma_list_open_files`. Pastikan file aktif memiliki key yang diminta. Reconnect hanya jika probe menunjukkan koneksi terputus atau tidak sehat.
- Jangan hardcode nomor port WebSocket. Gunakan transport dan port fallback yang dilaporkan MCP saat ini.
- Perlakukan operasi Figma sebagai **read-only secara default**. Jangan mengubah, membuat, memindah, memberi komentar, mengimpor, atau menghapus elemen desain, variabel, maupun aset tanpa persetujuan eksplisit pengguna untuk tindakan tersebut. Inspeksi baca saja juga harus sesuai otorisasi task. Persetujuan implementasi Flutter tidak otomatis menjadi persetujuan untuk mengubah Figma.
- Pilih operasi Desktop Bridge/Plugin API daripada permintaan REST bila keduanya tersedia. Hindari REST yang tidak diperlukan agar penggunaan kuota dan risiko rate limit tetap rendah; jika operasi tertentu hanya tersedia lewat REST, batasi permintaan pada data yang dibutuhkan dan laporkan jalur tersebut.
- Jangan pernah menampilkan, menyalin ke dokumentasi/kode, atau mencatat access token, OAuth token, secret, maupun credential lain. Laporkan status credential secara ringkas tanpa nilai rahasia.
- Gunakan kembali hasil inspeksi, screenshot, spesifikasi, dan aset yang sudah tersimpan selama masih cocok dengan file, node, dan revisi yang diminta. Verifikasi ulang hanya jika konteks mungkin berubah atau bukti lama tidak lagi sesuai.
- Baca node dan properti yang relevan saja. Utamakan `nodeIds` spesifik dan kedalaman seperlunya; jangan mengambil seluruh document tree berulang kali jika data node yang dibutuhkan sudah tersedia.
- Jangan mengarang ukuran, warna, typography, state, atau spesifikasi desain saat Figma/Bridge tidak dapat diakses. Nyatakan data yang gagal dibaca dan minta screenshot, ekspor aset, atau nilai spesifikasi yang diperlukan.
- Saat implementasi Flutter UI diminta dan disetujui, ikuti spesifikasi aktual dari Figma. Pertahankan arsitektur proyek, komponen reusable, standar coding, proteksi data, dan aturan keamanan yang sudah berlaku. Catat bagian yang masih belum terverifikasi dan jangan menyebut hasil pixel-perfect tanpa perbandingan visual.
